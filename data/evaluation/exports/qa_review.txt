## 1. Core System Architecture

CloudNote Pro operates on a multi-tenant cloud architecture separated into three primary layers:

1. **Client Layer:** Cross-platform applications built with Electron (macOS, Windows), React (Web), and Swift/Kotlin (iOS, Android).
2. **API Gateway & Sync Engine:** A real-time Conflict-Free Replicated Data Type (CRDT) synchronization service written in Rust that merges concurrent edits with sub-50ms latency.
3. **Storage Layer:**
- **Metadata & Permissions:** PostgreSQL cluster with row-level security.
- **Document Blobs & Media:** AES-256 encrypted object storage with automated regional replication.
- **Search Index:** Vector and keyword hybrid search index for instant workspace retrieval.

## 3. Troubleshooting Common Sync Conflicts

### Symptoms
Users editing a document offline may occasionally notice a banner stating: *"Sync Conflict Detected: A copy of your local edits has been saved."*

### Root Cause
While the CRDT engine automatically merges text edits, structural conflicts can occur when one user deletes a parent folder while another offline user adds new documents inside that same folder.

### Resolution Steps
1. Open the **Conflict Resolution Drawer** from the left sidebar.
2. Compare the **Local Version** timestamp against the **Cloud Version** timestamp.
3. Select **Keep Both** to restore the deleted folder structure alongside your offline notes, or **Merge into Active Workspace** to relocate the orphaned notes to your root directory.

• Vector database — The vector database is an index of the embeddings, the associated text, and
metadata. The index is optimized for search and retrieval.
• Retriever — For the user query, the retriever fetches the relevant context from the vector
database and ranks the responses based on business requirements.
• Foundation model — The foundation model for a RAG system is typically an LLM. By processing
the context and the prompt, the foundation model generates and formats a response for the
user.
• Guardrails — Guardrails are designed to make sure that the query, prompt, retrieved context,
and LLM response are accurate, responsible, ethical, and free of hallucinations and bias.

Organizations often have various sources of structured and unstructured data. This guide focuses

files, internal wikis, technical documents, public facing websites, knowledge bases, or others. If
you want a foundation model that can answer questions about unstructured data, the following
options are available:
• Train a new foundation model by using your custom documents and other training data
• Fine-tune an existing foundation model by using data from your custom documents
• Use in-context learning to pass a document to the foundation model when you ask a question
• Use a Retrieval Augmented Generation (RAG) approach

Broadly speaking, the RAG process is four steps. The first step is done once, and the other three
steps are done as many times as needed:
1. You create embeddings to ingest the internal documents into a vector database. Embeddings
are numeric representations of text in the documents that capture the semantic or contextual
meaning of the data. A vector database is essentially a database of these embeddings, and it is
sometimes called a vector store or vector index. This step requires data cleaning, formatting, and
chunking, but this is a one-time, upfront activity.
2. A human submits a query in natural language.
3. An orchestrator performs a similarity search in the vector database and retrieves the relevant
data. The orchestrator adds the retrieved data (also known as context) to the prompt that
contains the query.

Customer Query:
We are hitting a 429 Too Many Requests error when running our nightly backup script via the REST API. Our plan says we get 1,000 requests per minute, and our script only sends about 300. Why is it getting throttled?
Agent Response:
Great question. While the workspace limit is 1,000 requests per minute across all endpoints, the `/v2/notes/export` endpoint has a dedicated burst limit of 60 requests per minute due to payload size. Implementing an exponential backoff or batching up to 25 note IDs per request will keep you well within the burst threshold.
